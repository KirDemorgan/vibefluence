# 0006. Фейковый GitLab как основа тестов и dev-режима

## Контекст

Реальный GitLab и корпоративный инстанс в этой разработке недоступны. Тесты должны проверять интеграцию, включая режимы отказа, а разработчику нужен запуск без внешних систем.

## Решение

Пакет `internal/testing/fakegitlab` реализует нужные эндпоинты API v4 в памяти: дерево с keyset и offset пагинацией, файлы и blob, коммиты с действиями, MR, мердж, пайплайны. Идентификаторы blob совпадают с git. Режимы отказа настраиваются: 401, 405, 409, 429, `ci_must_pass`, `not_approved`, конфликт, запрет мерджа ботом, инъекция ошибок.

Тот же код запускается как `cmd/fakegitlab` с демо-данными для `make dev`.

## Последствия

- Интеграционные тесты быстрые и детерминированные.
- Поведение фейка отражает документацию GitLab, а не сам GitLab: расхождения возможны. Контрактные тесты на записанных ответах и ручная проверка на корпоративном GitLab закрывают этот риск.
- Любое новое обращение клиента к GitLab сначала добавляется в фейк вместе с тестами.
