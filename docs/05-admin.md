# Руководство администратора

Пометки: **[V]** проверено на фейковом GitLab или в документации, **[A]** предположение, проверить на вашем GitLab, **[?]** неизвестно. Реальный GitLab при разработке не использовался, поэтому всё, что касается поведения вашего сервера, нужно пройти по чек-листу в конце.

## Что нужно от GitLab

1. Пользователь-бот (по умолчанию `vibefluence-bot`, имя задаёт `gitlab.botUsername`). Сервис пишет в лог предупреждение, если токен принадлежит другому пользователю: правила CI по пользователю тогда не сработают [V].
2. Personal или project access token бота со scope `api`. Нужны чтение репозитория, создание коммитов и MR, мердж и удаление ветки [A: минимальный набор scope проверить, `read_api` для чтения достаточно, но запись требует `api`].
3. Роль в проекте не ниже Developer и право мерджить в default-ветку. Если default-ветка защищена, бота нужно внести в «Allowed to merge». Пушить в защищённую ветку боту не нужно: коммиты уходят в ветки `vibefluence/<slug>-<id>` [V по коду, поведение защиты проверить].
4. Ветки `vibefluence/*` не должны быть защищены правилом, запрещающим создание коммитов через API [A].

Токен передаётся только переменной окружения `VIBEFLUENCE_GITLAB_TOKEN`. В YAML-конфиге такого поля нет и быть не может [V]. Хранение и ротация токена зависят от платформы запуска (секреты Docker, Kubernetes, Vault): шифрования на диске в сервисе нет.

## Режим только для чтения (демо)

Без `VIBEFLUENCE_GITLAB_TOKEN` сервис стартует в режиме чтения [V на фейковом GitLab]: токен не отправляется, проверка токена в `/readyz` пропускается, публикация, сохранение и удаление черновиков отвечают `403 read_only`, а интерфейс скрывает «New document», «Edit» и раздел черновиков. Читаются только проекты, доступные анонимно: публичные проекты GitLab [A, поведение реального GitLab с анонимными запросами к API проверить]. Для приватных проектов без токена GitLab вернёт 404, и репозиторий покажется недоступным. Для демонстрации без реального GitLab запустите `backend/bin/fakegitlab -public` и приложение без токена.

## Защита CI репозитория

Сервис не пытается обойти CI. Если пайплайн запускается, MR остаётся открытым и никогда не мерджится автоматически.

Мердж создаёт коммит на default-ветке. Правило только по префиксу ветки этот пайплайн не остановит, поэтому в `.gitlab-ci.yml` каждого подключаемого репозитория нужен фильтр и по пользователю [A, переменные и синтаксис проверить на вашей версии]:

```yaml
workflow:
  rules:
    - if: '$GITLAB_USER_LOGIN == "vibefluence-bot"'
      when: never
    - if: '$CI_COMMIT_BRANCH =~ /^vibefluence\//'
      when: never
    - if: '$CI_MERGE_REQUEST_SOURCE_BRANCH_NAME =~ /^vibefluence\//'
      when: never
    # остальные правила репозитория
```

Страховка во время выполнения: после создания MR сервис ждёт две секунды, проверяет пайплайны ветки и MR и, если нашёл, не мерджит [V]. Гонку «пайплайн ещё не создан» это не устраняет. Если нужен режим без автомерджа, задайте `autoMerge: false` для репозитория: сервис создаст MR и остановится [V].

Если в проекте включено «Pipelines must succeed», а пайплайна для MR нет, GitLab может запретить мердж [?]. В этом случае MR останется открытым, причина (`detailed_merge_status`) показывается в интерфейсе [V по фейку].

## Обновление индекса

Сервис опрашивает default-ветку раз в 60 секунд и после собственного мерджа обновляет индекс сразу [V]. Чтобы изменения от других людей появлялись мгновенно, добавьте webhook (Push events) на `https://<host>/api/v1/webhooks/gitlab` и задайте секрет через `VIBEFLUENCE_GITLAB_WEBHOOK_SECRET`. GitLab передаёт его в заголовке `X-Gitlab-Token`. Без секрета эндпоинт отвечает 404 [V].

## Эксплуатация

| Что | Как |
|---|---|
| Liveness / readiness | `GET /healthz`, `GET /readyz` (проверяет токен в GitLab, результат кэшируется на 30 с, при ошибке на 5 с) |
| Метрики | `GET /metrics`, формат Prometheus: `vibefluence_http_requests_total` и `vibefluence_http_request_duration_seconds` с метками `route`, `method`, `status` |
| Лимит записи | `server.writeRateLimitPerMinute` (по умолчанию 120 на IP, 0 или отрицательное значение отключает); считаются изменяющие запросы к `/api/` и все запросы к `/mcp`, при превышении `429` и `Retry-After` |
| Заголовки | CSP (`script-src 'self'`, без inline-скриптов), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, COOP |
| Данные | `server.dataDir`: черновики интерфейса в `drafts/` (файлы 0600, каталоги 0700). Это единственное состояние, остальное берётся из GitLab |
| Логи | JSON или text, `X-Request-Id` в каждом ответе и записи |

Сервис не аутентифицирует пользователей и не должен быть доступен снаружи внутреннего контура. `/metrics` отдаётся на том же порту без авторизации: закройте его на обратном прокси, если порт виден за пределами мониторинга. Rate limit считает адрес TCP-соединения, за обратным прокси он будет общим для всех, поэтому при необходимости лимитируйте на прокси.

Запросы с `Origin` или `Sec-Fetch-Site` от другого сайта отклоняются для всех изменяющих методов (`http.CrossOriginProtection`), клиенты без этих заголовков (curl, MCP-агенты) проходят. Обратный прокси должен передавать исходный заголовок `Host`, иначе браузерные записи получат 403. От DNS rebinding это не защищает: не открывайте сервис за пределы внутреннего контура и ограничьте допустимые `Host` на прокси [A].

OpenTelemetry-трассировки нет: решение отложено, метрик и логов с request id хватает для первой версии.

## Чек-лист первого подключения

1. Создан бот, выдан токен `api`, бот добавлен в проект и может мерджить в default-ветку.
2. В `.gitlab-ci.yml` добавлены правила `workflow:rules` выше; в тестовой ветке проверено, что пайплайн не создаётся.
3. Сервис запущен, `GET /readyz` отвечает 200, в логах нет предупреждения про другого пользователя токена.
4. Из интерфейса опубликован тестовый документ: появился MR, он смерджен, на default-ветке нет пайплайна.
5. Опубликован документ при выключенном `autoMerge`: MR создан и остался открытым.
6. Настроен webhook, после ручного коммита документ появляется без ожидания минуты.
