# Vibefluence: анализ конкурентов и реализуемости

Дата: 2026-10-22. Статус: черновик на согласование.

> Обновление: решением заказчика Confluence-мост вынесен из проекта (разделы 3.3 и часть рисков остаются как справочный материал). Принятые решения: [03-decisions.md](03-decisions.md), актуальный бэклог: [02-backlog.md](02-backlog.md).

Пометки: **[V]** подтверждено документацией или поиском в этой сессии, **[A]** моё предположение, нужно проверить, **[?]** не удалось выяснить.

## 1. Что строим

Агентский «Confluence» поверх Markdown в git-репозиториях:

- читаем `docs/` (путь настраивается) из подключённых репозиториев и показываем деревом;
- пишем обратно: новый документ из UI превращается в коммит;
- документ со статусом `draft` не попадает в мастер, не-draft вливается в мастер автоматически;
- мост к self-hosted Confluence (версии 2021, 2022, 2026);
- бэкенд Go, фронтенд Angular + Taiga UI, дизайн в духе Apple.

## 2. Конкуренты и аналоги

| Решение | Что делает | Где проигрывает нашей идее |
|---|---|---|
| **GitLab Wiki** | Отдельный git-репозиторий на проект, Markdown/AsciiDoc/Org, редактор в браузере, дерево в сайдбаре, история [V] | Wiki живёт отдельно от кода; нет черновиков и ревью [V]; поиск только по заголовкам [V]; нет агрегации по репозиториям; сайдбар режется на 5000 записей [V] |
| **Wiki.js** | Страницы в БД, опциональная двусторонняя git-синхронизация [V] | Репозиторий должен быть выделенный под Wiki.js, подпапка не поддерживается [V]; синхронизация по расписанию, не мгновенная [V]; наш кейс «папка docs в боевом репозитории» не закрывает |
| **GitBook** | Git Sync с GitHub/GitLab в обе стороны [V] | SaaS, хостинг только у них [V]; self-host невозможен |
| **Backstage TechDocs (MkDocs)** | Docs-as-code, сборка из репозиториев | Встроенного редактора в браузере нет [V]; в Grab написали свой редактор, который собирает правки в один коммит и открывает MR [V]. Это прямое подтверждение, что потребность реальная, а готового решения нет |
| **Docusaurus и подобные генераторы** | Статический сайт из Markdown | Только чтение, правка через репозиторий [V] |
| **Outline, Docmost** | Современные вики в стиле Notion | Контент в своей БД; git-синхронизацию не подтвердил [?] |
| **Otter Wiki** | Вики, хранящая контент в git [V] | Один репозиторий, нет мульти-репо и Confluence-моста [A] |
| **mdlive и локальные просмотрщики** | Рендер Markdown рядом с агентом, правка в браузере [V] | Локальный инструмент одного разработчика, не командный портал |
| **Spec Kit, Kiro и т.п.** | Генерируют spec.md, plan, tasks в репозитории [V] | Это источники контента, а не UI. Показывать их артефакты нам и нужно. Готового веб-вьюера для них не нашёл [?] |
| **Confluence** | Эталон корпоративной вики | Контент в БД Atlassian, не в git; агентам неудобно; Server закрыт, Data Center сворачивается (см. раздел 4) |

### Где у нас реальная ниша

1. Мульти-репо вид на документы из боевых репозиториев без выделенного вики-репозитория.
2. Единый поток записи: UI, коммит, статус draft/published.
3. Знание о типах агентских артефактов (тикет, спека, ADR, план) через front matter.
4. Мост в Confluence для организаций, где «официальная» вики всё ещё Confluence.
5. Нормальный UX. У конкурентов он либо корпоративный, либо инженерный.

### Моё мнение (спорю там, где вижу риск)

- **Идея жизнеспособна, но узкая.** Главный реальный конкурент не внешний продукт, а «GitLab Wiki + MkDocs + веб-редактор GitLab». Выигрыш должен быть в UX и агрегации, а не в самом факте «Markdown в git».
- **Confluence-мост не стоит делать в первой версии.** Это самый дорогой и самый неопределённый кусок: три версии, которые не проверить на живом стенде. Предлагаю сначала довести ядро, потом мост за интерфейсом-адаптером.
- **«Не-драфт сразу в мастер» без ревью опасно.** Для команд с агентами это ещё и канал для мусора в основной ветке. Рекомендую режим на уровне репозитория: `direct` (как ты хочешь) или `merge-request` с автомёрджем.
- **«Не типичный интерфейс» плюс Taiga UI.** Taiga готовая библиотека со своим характером. Придётся серьёзно кастомизировать тему. В v5 есть поддержка liquid glass для TabBar [V], это в нужную сторону, но дизайн-система поверх всё равно потребуется.

## 3. Реализуемость по блокам

### 3.1 GitLab: чтение и запись

- Дерево: `GET /projects/:id/repository/tree` с `recursive` и keyset-пагинацией [V]. Лимиты на рекурсивный обход больших репозиториев в документации не описаны [?], поэтому ограничиваемся `path=docs` и кэшем.
- Запись нескольких файлов одним коммитом: `POST /projects/:id/repository/commits` с `actions[]` (create, update, delete, move) [V]. Есть `last_commit_id` для update/move/delete [V]. Это готовая оптимистичная блокировка против гонок «агент и человек правят один файл».
- Ветка под черновик: тот же эндпоинт с `start_branch` создаёт новую ветку [V].
- Дифф: `GET .../commits/:sha/diff` и `compare`, у больших файлов флаги `collapsed` и `too_large` [V].
- Размер запроса: больше 20 МБ ограничивается по частоте, больше 300 МБ отклоняется [V]. Для Markdown это не проблема, картинки нужно загружать отдельно.

### 3.2 Идея с отдельным пользователем-мерджером

Project access token создаёт бот-пользователя с ролью токена [V]. Боты не занимают платные места [V]. На self-managed токены доступны на любой лицензии, на GitLab.com только Premium и выше [V]. Токен живёт максимум 365 дней по умолчанию, админ может поменять с 17.6 [V]. Ротацию придётся автоматизировать или хотя бы напоминать.

Пушить в защищённую ветку можно по роли: «Allowed to push» задаётся ролями Developers/Maintainers [V]. Точечно добавить конкретного пользователя можно только в Premium и Ultimate [V]. Не нашёл подтверждения, как именно ведёт себя Commits API с токеном Maintainer на защищённой ветке [?]. Исходя из документации по ролям, это должно работать, если в «Allowed to push» включены Maintainers [A]. **Проверить на реальном GitLab нельзя, поэтому закладываем два режима и фича-флаг «MR вместо прямого пуша».**

Про «пайплайн, который не будет ридипойтиться»: отдельный пайплайн не нужен. Сервис Vibefluence сам ходит в API с токеном бота, никакого CI/CD вообще. Это упрощает задачу, а не усложняет. [A]

### 3.3 Confluence 2021 / 2022 / 2026

Сопоставление версий (даты третьих источников, не Atlassian [V с оговоркой]):

| Версия | Выпуск | Поддержка |
|---|---|---|
| 7.13 LTS | 08.2021 | закончилась 17.08.2023 |
| 7.19 LTS | 07.2022 | закончилась 13.12.2024 |
| 9.x / 9.2 LTS | дату выпуска не выяснил [?] | 9.2 LTS до 10.12.2026 по трекеру; 9.0 по нему же уже закрыта |

Что известно:

- Personal access tokens доступны с 7.9, то есть во всех трёх версиях [V].
- Basic auth блокировалась с 7.16, в 10.0 отключена по умолчанию [V]. Нужно, чтобы клиент не зависел от basic auth.
- Для создания страниц на Server/DC нужен storage format (XHTML) [V]. Значит, нужен конвертер Markdown в storage format. Готовые Python-инструменты это делают (md2cf) [V], на Go готового зрелого, насколько я нашёл, нет [?].
- Различия REST между 7.13, 7.19 и 9.x по этому поиску не выяснил [?]. Реальную совместимость можно проверить только на стенде.
- Атлассиан прекращает продажу новых лицензий Data Center 30.03.2026, подписки истекают 28.03.2029 [V, третий источник]. **Рынок моста сжимается.** Версии 2021 и 2022 уже вне поддержки, поддерживаем их ради легаси-инсталляций.

Реалистичный путь: набор contract-тестов на записанных ответах (VCR) плюс контейнерные стенды Confluence DC для трёх версий, если лицензия позволяет (триал-лицензия [A]). Без стенда обещать «поддержку 7.13/7.19/9.x» нельзя, это будет «заявлена, не проверена».

### 3.4 Стек

- **Go**: версия 1.27.3 установлена локально. Библиотеки на выбор, нужно согласовать: роутер chi, клиент GitLab `gitlab.com/gitlab-org/api/client-go` (старый xanzy/go-gitlab помечен deprecated, новый пока в основном поддерживается сообществом [V]), рендер Markdown goldmark [A], хранилище и поиск (см. вопросы).
- **Angular + Taiga UI**: по поиску Angular 22 (22.0.6 от 08.07.2026), с 21-й версии новые приложения по умолчанию без Zone.js, Angular 23 запланирован на июнь 2027 [V, третий источник]. Taiga UI 5.x (5.20.0 от 17.08.2026) требует Angular 19+, основан на signal-инпутах и Vite/esbuild [V]. Точные версии перед стартом сверить с npm.

## 4. Риски

1. **Невозможность проверить на реальных GitLab и Confluence.** Смягчение: адаптеры, контрактные тесты, локальный GitLab в Docker для CI (Community Edition, [A]).
2. **Прямой пуш в мастер.** Смягчение: режим на репозиторий, аудит-лог, откат через revert-коммит.
3. **Гонки правок.** Смягчение: `last_commit_id`, показ конфликта в UI.
4. **Токены.** Хранение зашифрованным, ротация, минимальные права.
5. **Размер деревьев и скорость.** Кэш индекса, инкрементальное обновление по вебхукам.
6. **Дизайн.** Самый субъективный пункт. Нужен прототип в Figma или HTML до написания компонентов.
7. **Сжатие рынка Confluence DC.**

## 5. Вердикт

Делать имеет смысл как **git-first портал документации для команд с AI-агентами**, с Confluence-мостом вторым этапом. Реализуемо на заявленном стеке. Неопределённость только в проверке на реальных интеграциях.
