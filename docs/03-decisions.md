# Vibefluence: решения и дизайн

Дата: 2026-10-22. Статус: на согласование, код не начат.

Пометки: **[V]** подтверждено документацией, **[A]** предположение, **[?]** не выяснено. Всё, что касается GitLab, мы проверить на живом инстансе не можем, поэтому критичные места закрываются тестами на фейковом GitLab и понятными ошибками в UI. Окончательную проверку делает команда локально на корпоративном GitLab.

## 1. Принятые решения

| Тема | Решение |
|---|---|
| Confluence | Вне проекта. В icebox |
| Аудитория | Внутренняя команда, внутренний контур, только GitLab |
| Аутентификация | Нет. Сервис за внутренней сетью |
| Формат контента | Только Markdown. Диаграммы в icebox |
| Совместная правка | Нет |
| Хранилище контента | Нет. Источник истины default-ветка в GitLab |
| Запись в GitLab | Отдельная ветка с префиксом, MR, мердж в default-ветку. Пайплайны отключает CI-конфиг репозитория, при его отсутствии не мерджим |
| Draft | Статус страницы. Отличие одно: не уходит в репозиторий автоматически |

| Агенты | MCP-сервер |
| Структура | Монорепа: `backend/` и `frontend/` |
| Качество | Продакшн-уровень, максимум тестов, фронтенд проработан по дизайну |

## 2. Структура монорепы

```
Vibefluence/
  backend/                 Go-модуль
    cmd/vibefluence/       точка входа
    internal/
      config/              конфиг и валидация
      gitlab/              клиент GitLab API
      docs/                модель документа, front matter, дерево
      index/               in-memory индекс и поиск
      drafts/              хранилище черновиков на диске
      publish/             поток ветка -> MR -> мердж
      api/                 HTTP API для UI
      mcp/                 MCP-сервер для агентов
      testing/fakegitlab/  фейковый GitLab для тестов и dev-режима
  frontend/                Angular + Taiga UI
  deploy/                  Dockerfile, compose
  docs/                    документация проекта
  Makefile                 единые команды: dev, test, lint, build
```

Продакшн: один бинарник Go, внутри которого через `embed` лежит собранный фронтенд. Один контейнер, ничего лишнего. В разработке: Angular dev-server с прокси на бэкенд. [A]

Текущие `main.go` и `go.mod` из шаблона GoLand переедут в `backend/`, шаблонный код будет удалён.

## 3. Чтение: как обойтись без хранилища

Источник истины default-ветка GitLab. Читаем только её, поэтому файл, добавленный в чужом MR, не виден, пока MR не смерджен. Это решает вашу первую проблему «файл должен появиться только вместе с мерджем MR» само по себе.

Схема загрузки:

1. `GET /projects/:id/repository/tree?path=docs&recursive=true&pagination=keyset` возвращает список файлов и blob-id [V]. Запрос ограничен путём, размер репозитория не важен.
2. Содержимое файла кэшируется по blob-id. Blob-id неизменяем, поэтому кэш никогда не протухает, инвалидировать нечего. Скачиваем только новые blob-ы.
3. Поисковый индекс строится в памяти из кэшированных текстов. Для десятков и сотен документов этого достаточно, отдельная БД не нужна.
4. Обновление дерева: webhook на push в default-ветку, опрос раз в 60 секунд как запасной путь, и немедленное обновление после нашего собственного мерджа.

Запасной вариант для полной выгрузки: `GET /projects/:id/repository/archive?path=docs` отдаёт архив только нужной папки одним запросом [V]. Ограничение 5 запросов в минуту документировано для GitLab.com, для self-managed не выяснил [?], поэтому основным делаем tree + blob-кэш.

Если в репозитории нет папки `docs/`, показываем пустое состояние, а не ошибку.

## 4. Draft и видимость

Единый источник истины: поле `status` во front matter.

```
---
title: План миграции
status: draft        # draft | published
type: spec           # необязательно
---
```

Правила:

| Ситуация | Что происходит |
|---|---|
| В default-ветке файл с `status: draft` | Скрыт: нет в дереве, поиске, списках и MCP. Прямая ссылка даёт 404 |
| В default-ветке файл без `status` | Считается `published` [A, подтвердить] |
| Битый front matter | Показываем документ с предупреждением и пишем в лог |
| Пользователь в UI сохраняет с `status: draft` | Рабочая копия на сервере, в репозиторий не уходит |
| Пользователь в UI публикует (`status: published`) | Ветка, MR, мердж, черновик удаляется |
| Переключатель Draft/Published в UI | Просто правит то же поле `status` в редакторе |

Рабочие копии (черновики) лежат файлами на диске сервера (`data/drafts/`), одна копия на документ, без БД. [A] Они видны в отдельном разделе «Черновики», помеченные как draft. Для редактирования существующего документа черновик хранит blob-id основы, чтобы при публикации обнаружить конфликт.

Снятие с публикации (вернуть в draft уже смерджённый документ) это отдельное действие «Unpublish», которое делает MR с `status: draft`. В первую версию не входит.

## 5. Запись: MR без пайплайнов

Поток публикации:

1. Ветка `vibefluence/<slug>-<короткий-id>` от default-ветки, коммит через Commits API с `start_branch` [V]. Для существующих файлов `last_commit_id` даёт защиту от гонок [V].
2. Создание MR (`source_branch`, `target_branch`, `title`) [V].
3. Мердж `PUT .../merge` с `should_remove_source_branch`, `sha` (должен совпасть с HEAD ветки) и своим `merge_commit_message` [V].
4. Обновление индекса и показ документа.

Как не запускать CI (решение заказчика): сервис ничего не хачит. Подключаемый репозиторий сам должен быть настроен в `.gitlab-ci.yml` так, чтобы пайплайны для действий Vibefluence не создавались. Если репозиторий не настроен, мы ничего не мерджим: MR остаётся открытым, чтобы не запускать чужой CI/CD. Директивы `[skip ci]` не используем: документация не подтверждает их работу для Commits API [?], для MR-пайплайнов они требуют версию GitLab с флагом `ci_skip_pipeline_from_mr_title` (по умолчанию с 19.5) [V], а для merge commit из шаблона не работают [V].

Важная тонкость: мердж создаёт коммит на **default-ветке**, и пайплайн на ней запустится, даже если ветка `vibefluence/...` была исключена. Правило по префиксу ветки этого не покрывает. Поэтому в CI-файле репозитория нужно правило не только по ветке, но и по пользователю, который запускает пайплайн (бот). Пример для администратора [A, переменные `CI_COMMIT_BRANCH`, `CI_MERGE_REQUEST_SOURCE_BRANCH_NAME`, `GITLAB_USER_LOGIN` и синтаксис проверить на вашей версии GitLab]:

```yaml
workflow:
  rules:
    - if: '$GITLAB_USER_LOGIN == "vibefluence-bot"'
      when: never
    - if: '$CI_COMMIT_BRANCH =~ /^vibefluence\//'
      when: never
    - if: '$CI_MERGE_REQUEST_SOURCE_BRANCH_NAME =~ /^vibefluence\//'
      when: never
    # ... остальные ваши правила
```

Защита во время выполнения, когда мы не доверяем настройке:

1. После создания MR сервис проверяет, создался ли пайплайн для ветки или MR (эндпоинты списка пайплайнов проверим при реализации [A]). Небольшая пауза нужна, потому что пайплайн создаётся асинхронно.
2. Если пайплайн есть, не мерджим, оставляем MR открытым и показываем причину.
3. Дополнительно режим «только MR»: для репозитория в конфиге можно запретить автомердж совсем.

Честно: гонка «пайплайн ещё не создан, мы уже смерджили» полностью не устранима снаружи. Поэтому главная гарантия это корректный CI-конфиг репозитория, а проверка во время выполнения лишь страховка. Пайплайн на default-ветке после нашего мерджа мы вообще предотвратить не можем, только правило пользователя в CI-файле.

Что может заблокировать мердж (ошибка 405 или статус `detailed_merge_status`) [V]:

| Причина | Статус |
|---|---|
| Включено «Pipelines must succeed», пайплайнов нет или он пропущен | `ci_must_pass`. Пропущенные пайплайны блокируют, пока не включена опция «Skipped pipelines are considered successful»; при отсутствии `.gitlab-ci.yml` мердж блокируется всегда [V] |
| Нужен approval | `not_approved` |
| Есть нерешённые обсуждения | `discussions_not_resolved` |
| Бот не имеет права мерджить | 401 |

Это **предусловия на стороне вашего GitLab**, которые мы не контролируем. Заметьте: если включено «Pipelines must succeed», а пайплайны для бота отключены правилом выше, мердж всё равно заблокирован (нет пайплайна), а опция «Skipped pipelines are considered successful» относится только к пропущенным, не к несуществующим пайплайнам [V]. Значит, для таких репозиториев эта настройка несовместима с автомерджем. Поэтому сервис не падает, а деградирует: если мердж запрещён, MR остаётся открытым, а UI показывает статус «Ждёт мерджа» со ссылкой и причиной из `detailed_merge_status`. Пользователь вмерживает руками, документ появится после этого. Список предусловий уйдёт в документацию для администратора.

Бот: project access token с ролью Maintainer, права `api` [A]. Токены живут максимум 365 дней по умолчанию [V], нужно предупреждение об истечении.

Подписи коммитов: автор технический бот. Имя человека берём из поля «Ваше имя» в UI (хранится в браузере) и пишем в трейлер сообщения коммита. [A]

## 6. MCP для агентов

Официальный Go SDK `github.com/modelcontextprotocol/go-sdk`, версия 1.7.0 от июля 2026 [V]. Поддержку Streamable HTTP в поиске не подтвердил [?], проверим при реализации. Сервер подключается в тот же бинарник по пути `/mcp`.

Инструменты:

| Инструмент | Назначение | По умолчанию |
|---|---|---|
| `list_repositories` | Список подключённых репозиториев | включён |
| `list_documents` | Дерево документов, фильтры по типу и статусу | включён |
| `read_document` | Текст документа и front matter | включён |
| `search_documents` | Поиск по тексту | включён |
| `save_draft` | Сохранить черновик на сервере | включён |
| `publish_document` | Запустить MR-поток | **выключен**, включается флагом |

Агенты и так могут писать файлы в `docs/` в рамках своего MR задачи, поэтому запись через MCP нужна как удобство, а не как основной путь. Сервер без аутентификации, поэтому запись через MCP по умолчанию ограничена черновиками.

## 7. Стратегия тестов

Цель: максимум покрытия без живого GitLab.

**Бэкенд**
- Юнит-тесты (табличные) на парсер front matter, правила видимости, построение дерева, MR-поток.
- Фейковый GitLab (`internal/testing/fakegitlab`) на `httptest`: реализует используемые эндпоинты и все режимы отказа (405, 409, `ci_must_pass`, `not_approved`, 401, rate limit, пагинация, 404 для отсутствующей папки). Он же даёт dev-режим без реального GitLab.
- Контрактные тесты на записанных ответах GitLab, чтобы потом сверить с корпоративным.
- Fuzz-тесты (стандартный `go test -fuzz`) на front matter и санитизацию Markdown.
- `-race`, `govulncheck`, статический анализ (`golangci-lint`). Порог покрытия для доменных пакетов, цифру предлагаю 85% [A].
- Опционально ночная интеграция с реальным GitLab CE в контейнере. Он тяжёлый и стартует минуты [A], поэтому не на каждый коммит.

**Фронтенд**
- Юнит и компонентные тесты на стандартном раннере Angular (проверить, какой в 22-й версии по умолчанию [?]).
- E2E на Playwright против бэкенда с фейковым GitLab, включая сценарии конфликта, «ждёт мерджа», draft.
- Проверки доступности (axe) и визуальная регрессия скриншотами. [A]

## 8. Фронтенд: продакшн-уровень

- Angular 22, standalone-компоненты, signals, без Zone.js (по умолчанию в новых приложениях с 21-й) [V, третий источник]. Версию сверить с npm.
- Taiga UI 5.x [V], кастомная тема поверх неё. Сначала прототип экранов, потом компоненты.
- Строгий TypeScript, angular-eslint, Prettier, бюджеты размера бандла, ленивые маршруты.
- Безопасность: санитизация отрендеренного Markdown на сервере и на клиенте, строгий CSP.
- Адаптив, тёмная тема, доступность WCAG 2.2 AA, командная палитра.
- Язык интерфейса: открытый вопрос.

## 10. Открытые вопросы (исходная постановка)

1. Файл без `status` считается опубликованным? (рекомендую да)
2. Черновики видны всем в разделе «Черновики»? Раз аутентификации нет, владельца у черновика нет.
3. MCP: запись только черновиками, `publish_document` за флагом. Подходит?
4. Язык интерфейса: только русский, только английский или оба?
5. Какая у ваших репозиториев default-ветка (в этом локальном репозитории `master`, шаблон GoLand дал `main`)? Настраиваем на репозиторий, по умолчанию ветка по умолчанию проекта.
6. В CI-конфиге репозиториев правило должно отсекать пайплайны и по префиксу ветки, и по пользователю-боту (иначе пайплайн запустится на default-ветке после мерджа). Подходит ли такой вариант, и как называется бот (в примере `vibefluence-bot`)?

8. Имя Go-модуля: оставить `Vibefluence` или заменить на путь вашего корпоративного GitLab?
